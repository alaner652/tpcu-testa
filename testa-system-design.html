Testa 考試平台:系統設計與架構構想

2026-11-13,吳宸麒,草稿 v0.2

Testa 是學校自建的線上考試系統,第一個用途是讓未入學的校外考生以白名單方式應考。第一版(MVP)做到「出題、發考、作答、三人評分、公布成績」一條龍,前端 Vue、後端 Java。

1目的與範圍

  • 現階段用途:招生單位對校外考生的入學考試。
  • 兩種施測方式都要能用:純線上(考生用自己的電腦)與電腦教室區網(考生在教室,監考在場)。同一套系統,只差部署位置與監考方式。
  • MVP 登入三種:考生、教師、管理員。管理員定位為系統維護者,不碰考卷內容。
  • 評分:申論題由三位評分者各自獨立評分,取平均。
  • 技術:前端 Vue 3 + TypeScript,後端 Java(Spring Boot)。
  • 保留項目:班級學生長期帳號、Email/簡訊邀請、更細的單位內角色。資料結構先預留,介面先不做。

設計原則:老師的學習成本優先。每種角色登入後只看到兩三個選單,不可逆的動作一律跳出確認。

2角色與權限

角色分三層,而且「角色跟著單位走」:同一個人在不同單位可以有不同角色。招生組和班級只是不同的「單位」,權限設計共用。

三層角色:系統、單位、考生互相隔離

第一層:系統管理員 資訊單位,人數很少
管帳號與單位建立單位、開教職員帳號
管系統系統設定、備份、操作紀錄
看不到題庫、答卷、分數
建立單位、指派單位負責人
第二層:單位內角色 例:招生組,之後的某個班級
單位負責人建立考試、匯入名單、指派角色、公布成績
出題者建立與編輯題庫
監考登入單、即時狀態、重設登入碼
評分者只看被指派的匿名答卷
匯入白名單、發登入單
第三層:考生
校外考生沒有帳號。准考證號加登入碼,只屬於一場考試
班級學生(保留)長期帳號,屬於某個班級

系統管理員碰不到考卷,評分者看不到考生身分,考生只看得到自己的考試。

MVP 先合併成四種

MVP 角色對應的完整角色登入方式登入後看到
系統管理員系統管理員帳號密碼使用者、單位、系統設定、操作紀錄
承辦人單位負責人 + 監考帳號密碼考試、名單、登入單、監考、成績
教師出題者 + 評分者帳號密碼題庫、評分
校外考生校外考生准考證號 + 登入碼自己的考試

承辦人與教師都走「教職員登入」,所以登入畫面仍然是考生、教職員兩個入口。如果組長希望只有三種角色,承辦人的工作可以併給教師,代價是名單與成績的權限會開得比較寬。

4一場考試的完整流程

從出題到公布成績共九步,考生只參與其中三步

  1. 建立題庫 教師選擇、填空、申論。設定配分與標準答案。
  2. 建立考試 承辦人選題庫、設定時間與時長。
  3. 匯入考生名單 承辦人上傳 Excel 或 CSV。系統檢查重複與缺漏,產生每人一組登入碼。
  4. 發登入單 承辦人列印紙本。純線上場次是否改用 Email 或簡訊,待確認。
  5. 考生登入並確認身分 考生輸入准考證號與登入碼。畫面顯示姓名與報考科系,考生確認後才進入。
  6. 作答 考生每次作答自動存到伺服器。剩餘時間由伺服器計算。斷線或換電腦後重新登入,從原進度繼續。
  7. 交卷 考生確認後交卷,時間到自動交卷。選擇題與填空題由系統立即批改。
  8. 三人評分 教師申論題由三位評分者匿名獨立評分。詳見下一節。
  9. 公布成績 承辦人全部評分完成後才能公布,並可匯出 Excel。

監考在第 5 到 7 步期間看即時狀態:未登入、作答中、已交卷,並可重設登入碼。

5三人評分設計

目標是公平且可說明:每位評分者看不到考生是誰,也看不到另外兩人打幾分,三人都送出後分數才鎖定並計算平均。

三人評分流程圖:匿名、獨立、鎖定後取平均

評分步驟說明

  1. 指派三位評分者 承辦人以考試為單位指派。系統檢查必須剛好三位。
  2. 匿名化 系統答卷改用隨機編號顯示,隱藏姓名與准考證號。每位評分者看到的答卷順序不同。
  3. 獨立評分 評分者 ×3逐題給分並可寫評語。送出前可修改,看不到其他人的分數。
    評分者甲16
    評分者乙18
    評分者丙14
    該題得分 = (16 + 18 + 14) ÷ 3 = 16.0
  4. 鎖定 系統三人都送出後,該答案鎖定並計算平均。未滿三人不計分,也不能公布成績。
  5. 差異標記 系統三人之中最高分與最低分的差距超過門檻時,標記給承辦人查看。門檻與處理方式待確認。
  6. 彙總 系統考生總分 = 自動批改得分 + 各申論題平均分的總和。

規則

項目設計
計算方式每一題各自取三人平均,再加總。不是先加總再平均,這樣每題的差異都看得到。
小數處理暫定每題平均四捨五入到小數一位。待確認。
匿名評分者看不到考生身分;評分期間看不到其他評分者的分數。
鎖定後修改評分者不能自行修改。只有承辦人可以「重開評分」,必須填理由,並寫入操作紀錄。
進度承辦人看到每位評分者的完成數,例如 12/40,看不到分數內容直到鎖定。
評分者缺席承辦人可以在該評分者尚未送出的答卷上換人,已送出的分數保留。
AI 評分建議MVP 不顯示,避免影響評分者獨立判斷。

6資料模型

資料表關係圖:紅色是為三人評分與單位角色新增的

線條表示兩張表有關聯。考試另外直接屬於一個單位;操作紀錄 audit_log 獨立存在,不畫線。

各表欄位

unit 單位

  • id
  • name
  • type:招生 / 班級

staff 教職員帳號

  • id
  • email、password_hash
  • name
  • is_system_admin

unit_role 單位角色

  • → unit
  • → staff
  • role:負責人 / 出題 / 監考 / 評分

bank 題庫

  • id、title
  • → unit
  • → staff(建立者)

question 題目

  • → bank
  • type、stem、points
  • content(選項、答案,JSON)
  • position

exam 考試

  • → unit、→ bank
  • start_at、duration
  • mode:線上 / 教室
  • status
  • 題目快照(發布時凍結)

candidate 考生

  • → exam
  • ticket(准考證號)
  • name、dept、seat
  • code_hash(登入碼)
  • status

attempt 作答

  • → candidate
  • started_at、deadline_at
  • submitted_at
  • anon_id(匿名編號)
  • auto_score、final_score

answer 答案

  • → attempt、→ question
  • content
  • auto_score
  • avg_score、locked

exam_grader 評分指派

  • → exam
  • → staff
  • 每場考試三筆

grading 評分紀錄

  • → answer
  • → staff(評分者)
  • score、comment
  • submitted_at
  • 每個申論答案三筆

audit_log 操作紀錄

  • who、when、action
  • target、reason
  • 只能新增,不能改

箭頭表示「屬於」。考試發布時把題目複製成快照,之後題庫再改也不影響已發布的考試。

班級學生之後要加入時,新增一張長期帳號的學生表,candidate 改為可以連到學生帳號即可,其餘資料表不動。

7部署方案

兩種方案用同一份程式與同一份 Docker Compose 設定,差別只在主機放哪裡。

部署架構圖:兩種方案跑同一套系統

A:純線上B:電腦教室區網
防作弊無法確認考生身邊狀況,只能記錄離開畫面次數供參考監考在場,可關閉對外網路
登入單需要 Email 或簡訊寄送(待確認)現場發紙本
網路風險考生家中斷線,靠自動儲存與重新登入續考區網穩定,不依賴對外網路
評分教師直接上線評分主機若只在區網,教師需在校內評分,或考後把主機接回校內網路

限制:純線上只能防君子。正式招生考試建議用方案 B,或線上報到加教室應考。系統兩種都支援,由承辦人建立考試時選擇。

8安全與稽核

風險做法
考生看到答案標準答案永遠不送到考生端,批改只在後端做
改前端時間多寫幾分鐘截止時間存在伺服器,過了就拒收
登入碼被猜登入碼雜湊後儲存;同一准考證號連續錯誤即暫時鎖定;監考可重設
代考或一人多處登入登入後顯示姓名供確認;同一考生同時只允許一個連線,新登入會踢掉舊的並記錄
教職員越權每個 API 都由後端檢查「這個人在這個單位有沒有這個角色」
評分不公匿名、獨立、三人平均、鎖定後不可改、重開需理由
事後爭議操作紀錄只增不改:登入、交卷、重設登入碼、重開評分、公布成績
個資考生資料只屬於該場考試,保存期限到期後刪除(期限待確認)
資料遺失每日備份;作答每次變動即存入資料庫

9MVP 範圍與開發順序

第一版要做

  • 三種登入:考生、教職員(教師與承辦人)、系統管理員
  • 題庫編輯:選擇、填空、申論,數學式
  • 考試建立、白名單匯入、登入單列印
  • 作答、自動儲存、計時、交卷、斷線續考
  • 自動批改與三人評分
  • 成績彙總、公布、匯出
  • 監考即時狀態、操作紀錄

第一版不做

  • 班級學生長期帳號
  • Email、簡訊邀請(確認需要再加)
  • AI 匯入題目、AI 評分建議
  • 視訊監考、鎖定瀏覽器
  • 題目隨機抽題、多份試卷
  • 與校務系統串接

開發順序

  1. 後端骨架與登入專案建立、資料表、教職員登入、單位與角色、權限檢查。
  2. 題庫把原型的題庫編輯器接上真的 API。
  3. 考試與名單建立考試、匯入白名單、產生登入碼、登入單。
  4. 考生作答考生登入、身分確認、作答、自動儲存、伺服器計時、交卷、自動批改。
  5. 三人評分指派、匿名、獨立評分、平均、鎖定、差異標記。
  6. 成績與監考彙總、公布、匯出、即時狀態。
  7. 部署與試考Docker Compose、備份、在電腦教室實際跑一場模擬考。

每一步完成後都能單獨展示。前四步完成即可進行不含申論題的考試。

10待確認事項

  • 角色數量:接受「系統管理員、承辦人、教師、考生」四種,還是只要三種(承辦人併入教師)?
  • 出題與評分迴避:出題者可以評自己出的題目嗎?
  • 系統管理員的緊急權限:需不需要在緊急狀況下進入單位查看?若需要,每次進入都留紀錄。
  • 平均的小數:每題平均取到小數幾位?總分是否再取整數?
  • 評分差異:三人差距多大算異常?異常時由承辦人裁定、請三人重評,還是加第四位評分者?
  • 純線上場次的登入單:要不要做 Email 或簡訊寄送?
  • 交卷後考生看到什麼:只顯示「已交卷」,還是可以看選擇題得分?成績公布後考生能不能登入查詢?
  • 考生資料保存多久:考試結束後多久刪除個資與答卷?
  • 主機與資料庫:學校提供哪種主機?資料庫用 PostgreSQL 還是學校慣用的其他資料庫?
  • 教職員帳號來源:由系統管理員手動建立,還是之後串接學校的單一登入?
